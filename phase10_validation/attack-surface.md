# Phase 10 attack surface (mapped before scenario design)

Version evidence: this checkout has no `HEAD` commit; all files are untracked. The manifest records SHA-256 hashes of production files before execution.

The user, retrieved content, provider output and tool proposals are untrusted. `ToolRequest` and `SecurityContext` enter `ExecutionGateway.execute`; the latter is authoritative only when constructed by the trusted host. The gateway copies both, invokes `PolicyEngine`, resolves cancellation targets from sandbox state, applies resource and destination checks, checks a gateway-local idempotency map and aggregate ledger, then consults an optional approval verifier. It writes a pre-execution audit event, executes the sandbox operation, updates aggregate/idempotency state, and writes a terminal event.

Trust boundaries: model to typed request; host identity/grants to capability evaluator; caller arguments to normalized schema; indirect order ID to stored owner/environment/symbol; decision to exact sandbox call; human authority to approval ledger; sandbox side effect to audit recorder. Principal and environment partition account state. Order IDs and transaction IDs are generated globally. Approval records can persist on a local filesystem; gateway idempotency and aggregate accounting are in memory. Audit may persist in JSONL. The gateway lock serializes one gateway instance, while the sandbox and approval manager own separate locks.

Security-relevant mutable state: account balances, orders, transactions, approval status, idempotency results, aggregate spent, and audit events. `evaluated_at` comes from the security context, so the trusted host must supply a trustworthy clock. The public gateway exposes snapshots for inspection; the internal sandbox is outside the intended agent API. Potential cross-component assumptions include consistency of capability selection, destination scope, aggregate accounting, approval consumption, idempotency replay, resource resolution, and terminal audit recording.
