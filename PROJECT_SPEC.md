\# Agent Firewall



\## Zero-Trust Runtime Security for Tool-Using Financial AI Agents



\## 1. Problem



AI agents increasingly interact with external tools and APIs.



In financial environments, those tools may expose capabilities such as:



\- reading balances;

\- reading positions;

\- creating/canceling orders;

\- transferring assets;

\- performing other sensitive operations.



Traditional LLM alignment alone is not a sufficient authorization mechanism.



The system must assume that:



\- the model may make mistakes;

\- prompts may contain malicious instructions;

\- external content may be adversarial;

\- tools may return untrusted content;

\- an agent may attempt actions outside its intended scope.



Therefore, sensitive tool execution requires an independent enforcement layer.



\---



\# 2. Product



Agent Firewall is a zero-trust runtime security layer placed between AI agents and protected tools.



Conceptually:



Agent

→ proposed tool call

→ Agent Firewall

→ authorized tool execution



Every protected action receives one of three decisions:



ALLOW



DENY



REQUIRE\_APPROVAL



\---



\# 3. Primary Goal



Demonstrate experimentally that deterministic runtime authorization can reduce successful adversarial/unauthorized financial-agent actions while preserving legitimate task completion.



\---



\# 4. Non-Goals



The initial project is NOT:



\- a production trading platform;

\- a wallet;

\- an exchange;

\- an AML system;

\- an investment adviser;

\- a generic antivirus;

\- a universal prompt-injection detector;

\- a replacement for model alignment;

\- a production system for real funds.



All financial execution occurs in a deterministic sandbox.



\---



\# 5. Trust Model



Trusted:



\- firewall policy configuration;

\- deterministic policy engine;

\- capability definitions;

\- approval authority;

\- validated tool schemas.



Untrusted:



\- LLM output;

\- user-provided external content where applicable;

\- webpages/documents;

\- arbitrary tool output unless explicitly trusted;

\- agent-generated tool arguments.



\---



\# 6. Core Components



\## Agent Adapter



Normalizes tool-call requests generated by an agent.



\## Tool Registry



Defines available tools and typed schemas.



\## Capability Engine



Determines whether an agent possesses the required capability.



\## Policy Engine



Evaluates deterministic authorization policies.



\## Risk Context



Tracks security-relevant context needed for policy evaluation.



\## Approval Manager



Handles actions requiring human authorization.



\## Execution Gateway



Executes a tool only after successful authorization.



\## Audit Recorder



Stores structured security decisions and execution outcomes.



\## Financial Sandbox



Provides deterministic financial tools without real funds.



\## Evaluation Harness



Executes benign and adversarial scenarios and computes metrics.

\# 8. Initial Policies



The first version should support rules equivalent to:



P01 — Unknown tools are denied.



P02 — Missing capabilities are denied.



P03 — Expired capabilities are denied.



P04 — Tool arguments must satisfy the registered schema.



P05 — Orders must satisfy symbol scope.



P06 — Orders must satisfy configured notional limits.



P07 — Sensitive actions may require human approval.



P08 — Withdrawal execution must follow explicit configured policy.



P09 — Denied actions must never reach tool execution.



P10 — Security evaluation failures fail closed.



Policies should be represented in a way that is inspectable and testable.

A01 — direct instruction attack



A02 — indirect prompt injection



A03 — unauthorized tool invocation



A04 — privilege escalation



A05 — argument/amount manipulation



A06 — approval bypass



A07 — excessive action



A08 — unauthorized tool chaining



A09 — malicious tool/external content influence



A10 — expired/stale capability use



A11 — malformed security-sensitive request



A12 — capability scope violation



The benchmark should eventually contain multiple distinct scenarios per category.



\---



\# 11. Benign Tasks



The evaluation dataset must also include legitimate workflows.



Examples:



\- read BTC market price;

\- inspect portfolio;

\- inspect open orders;

\- create an authorized small sandbox order;

\- cancel an authorized order;

\- request an action requiring approval and successfully complete it after valid approval.



Benign tasks are required to measure utility loss and false blocking.

\# 12. Evaluation Configurations



\## Baseline A — Unprotected Agent



Agent can access sandbox tools without Agent Firewall authorization.



Purpose:



Measure baseline vulnerability.



\## Baseline B — Basic Rules



Simple static allow/deny controls.



Purpose:



Determine whether sophisticated architecture actually improves over trivial safeguards.



\## System — Agent Firewall



Full capability + policy + approval + audit enforcement.

\# 13. Primary Metrics



\## Attack Success Rate



successful\_attacks / attempted\_attacks



A successful attack must have an explicit scenario-specific definition.



\## Unauthorized Action Rate



unauthorized\_actions\_executed / unauthorized\_actions\_attempted



\## Benign Task Success Rate



successfully\_completed\_benign\_tasks / benign\_tasks\_attempted



\## False Block Rate



legitimate\_actions\_incorrectly\_blocked / legitimate\_actions\_requested



\## Security Decision Latency



Measure p50/p95/p99 where useful.



\## End-to-End Task Latency



Measure total workflow latency.

\# 15. Security Invariants



Examples:



INV-01



A DENY decision can never result in tool execution.



INV-02



An agent lacking a required capability can never successfully execute the corresponding protected action.



INV-03



Expired capabilities never authorize execution.



INV-04



REQUIRE\_APPROVAL never executes before valid approval.



INV-05



Unknown protected tools fail closed.



INV-06



Tool arguments are validated before execution.



INV-07



Every protected execution produces an audit event.



These invariants require automated tests.

The project should support reproducing firewall decisions from recorded structured inputs where practical.

Which capability was required?



Which policies matched?

Did execution occur?

\# 22. Definition of Portfolio Success



The project is successful only if it produces credible evidence for questions such as:



How vulnerable was the baseline?



How much did Agent Firewall reduce attack success?



How many legitimate tasks were incorrectly blocked?



What was the latency overhead?



Which attack categories remain unsolved?



What security guarantees come from deterministic enforcement rather than model behavior?



The final README must explicitly discuss failures and limitations.
